Что уже сделано по этапам из папки `тз/`. Обновляется по ходу работы —
смотрите сюда, если забыли, на чём остановились.

## Этап 1. Каркас и деплой — готово

  в `CLAUDE.md`): сайт живёт на https://baka-page.eduard1414ed.workers.dev
  Правите файл на GitHub → через 1–2 минуты изменение видно на сайте.
- Воркер-посредник для входа в CMS через GitHub — настроен один раз,
  живёт отдельно: https://baki-cms-auth.eduard1414ed.workers.dev
  (код в папке `cms-auth/`, секреты — в панели Cloudflare, не в репозитории).
- Общий шаблон страницы: шапка (`src/components/Header.astro`) и подвал
  (`src/components/Footer.astro`) собраны в `src/layouts/Layout.astro`.
- Главная страница (`src/pages/index.astro`): название, описание, обложка,

- Картинки сжимаются автоматически, не больше 2 файлов на каждую

## Этап 2. Посты и админка — готово

- Схема поста: `src/content.config.ts` — поля по модели из `CLAUDE.md`
  (кроме `anime`, её подключим на этапе тайтлов). Файлы постов лежат
  в `src/content/posts/*.md`, там же тестовый пост-черновик
  (`test-zametka.md`) для проверки — можно удалить, когда надоест.
- Пять категорий (без «Интервью», убрали) и страницы `/category/[имя]/`
  с вкладками для переключения между категориями.
- Лента постов на главной странице с теми же вкладками. Карточка
  поста (`src/components/PostCard.astro`) сама выбирает вид: обложка,
  превью видео с YouTube или отрывок текста.
- Страница отдельного поста `/posts/[адрес]/`.
- Черновики (`draft: true`) не попадают ни в ленту, ни в категории,
  ни получают свою страницу.
- **Админка Sveltia CMS на `/admin`** — вход через GitHub (воркер
  `baki-cms-auth` с первого этапа). Публикация простого текстового
  поста, черновики/публикация — работает.
- **Редактор — 4 блока**, вставляются кнопкой на панели, каждый
  можно вставить где угодно в тексте:
  - «Изображение с подписью» — файл, альт-текст, подпись, ширина
    (в колонку / во всю ширину), источник со ссылкой, увеличение
    по клику. Несколько таких блоков подряд без текста между ними
    сайт сам собирает в галерею — сеткой (до 4 картинок) или
    каруселью со стрелочками (от 5). Отдельного блока «Галерея»
    в CMS специально нет — список картинок внутри своего компонента
    там ненадёжно сохранялся (несколько раз терял/портил данные),
    группировка на стороне сайта оказалась надёжнее.
  - «Спойлер» — два маркера, начало/конец, между ними обычный текст
    и другие блоки (в т.ч. картинки/галерея). Спрятанное лежит
    в `<template>`, не отдаётся поисковикам, раскрывается по клику.
  - «Спойлер (слово/фраза)» — для одного слова/части предложения,
    сплошная цветная плашка по ширине текста, раскрывается на том
    же месте.
  - «Видео» — пока только ссылка на YouTube. Свой файл через этот
    блок сознательно не грузим (упёрлись бы в лимит Cloudflare
    25 МБ на файл и в репозиторий не то место для видео) — загрузку
    на Hetzner сделаем на этапе «Выпуски и плеер», сразу как надо.
  - Логика блоков: `src/plugins/remark-*.mjs`, регистрация в CMS —
    `public/admin/index.html`.
- **Кнопки** — поле `buttons` (подпись + ссылка + стиль основная/
  второстепенная) было в схеме поста с первого этапа, теперь открыто
  в админке и показывается на странице поста под обложкой/видео.
  Иконка подставляется сама по домену ссылки (YouTube, Spotify,
  Apple, Boosty, Telegram) — `src/lib/linkIcon.mjs` +
  `src/components/PlatformIcon.astro`. Глобальный набор ссылок
  на площадки в подвале был готов ещё с первого этапа
  (`src/data/platforms.js`).
- **Сжатие картинок** — обложки постов Astro сжимала сама через
  `<Image>` (2 размера, webp) ещё с первого этапа. Картинки из
  блока «Изображение с подписью» и галереи теперь тоже сжимаются:
  после сборки отдельный шаг (`src/plugins/optimize-uploads-integration.mjs`)
  проходит по `public/images/uploads`, через `sharp` режет каждую
  в webp в двух размерах (640/1280 — телефон/десктоп) и убирает
  оригинал из итоговой сборки. Ленивая загрузка (`loading="lazy"`)
  у всех картинок в тексте уже стоит. Проверено на реальных
  картинках поста: 2.9 МБ → 1.1 МБ.
- Известная особенность: автосборка на Cloudflare время от времени
  подвисает или подхватывает пуш не до конца (частично — то есть
  часть файлов новая, часть старая, сайт выглядит битым; само
  чинится не всегда). Рабочий обход — `npx wrangler deploy` из
  папки проекта, заливает уже собранную `dist/` напрямую и всегда
  приводит сайт в консистентное состояние. Если после пуша сайт
  выглядит странно (старая версия или часть картинок не грузится) —
  `npm run build`, потом `npx wrangler deploy`.
  **Обновление (другая сессия, не записали вовремя):** основную причину
  нашли и починили — в настройках воркера на Cloudflare была включена
  галочка кэширования предыдущих версий, из-за неё edge-серверы иногда
  ещё отдавали старую версию сайта уже после того, как новая полностью
  задеплоилась. Галочку сняли — проблема стала заметно реже. Полностью
  ли пропала — не факт, поэтому обход через `wrangler deploy` выше
  оставляем в статусе как рабочий план на случай, если всё-таки
  проявится снова.

## Этап 3. Тайтлы — готово

- **Справочник тайтлов** — новая «полка» контента `src/content/anime/*.json`,
  поля по модели из `CLAUDE.md` (`id`, `shikimoriId`, `titleRu`, `titleOriginal`,
  `year`, `studio`, `poster`, `synopsis`, `url`). Схема — `src/content.config.ts`.
- **Поле `anime` у поста** — ссылка (или несколько) на тайтл из справочника.
  Заполняется само по разметке в тексте (см. ниже), руками вести не нужно.
  Astro проверяет тип ссылки, но не существование самого тайтла — опечатка
  в slug не ломает сборку, а просто тихо не создаёт связь.
- **Загрузчик данных `scripts/fetch-anime.mjs`** — отдельный скрипт, не часть
  сборки сайта. Запускается вручную:
  `node scripts/fetch-anime.mjs slug:поисковый_запрос` (можно несколько пар
  за раз, между тайтлами пауза 1.5 сек). Обложку сжимает в 2 webp-размера
  (320/640) в `public/anime/`, данные сохраняет в `src/content/anime/<slug>.json`.
  Сборка сайта (`npm run build`) эти файлы только читает — в сеть не ходит
  никогда, поэтому не зависит от того, доступны ли Shikimori и AniList.
- **Два источника данных, Shikimori основной + AniList запасной** —
  `scripts/anime-sources/shikimori.mjs` и `anilist.mjs`, оба одной формы
  (`id`, `label`, `find(запрос)`), скрипт перебирает их по порядку.
  Если тайтла нет в Shikimori — ищет в AniList; если нет нигде — понятное
  сообщение в консоли, без падения скрипта. Каждый раз печатает, какой
  тайтл нашёл и в каком источнике — чтобы можно было на глаз проверить,
  что подобралось верно (у обоих API поиск иногда путает непохожие
  названия). Третий источник добавляется отдельным модулем такой же формы,
  без переделки остального скрипта; в справочнике у каждого тайтла хранится,
  откуда взяты данные (`source`, `sourceId`).
  У AniList не бывает русских названий — `titleRu` в этом случае остаётся
  пустым, страницы `/anime` и `/anime/[slug]` в этом случае явно показывают
  оригинальное название и жёлтую плашку «нужен перевод» с указанием,
  в какой файл его вписать вручную.
- **Страница `/anime`** — сетка всех тайтлов из справочника, отсортирована
  по числу упоминаний в опубликованных постах (по алфавиту при равенстве).
- **Страница `/anime/[slug]`** — обложка, оригинальное и русское название,
  год, студия, ссылка на Shikimori, описание и список постов с упоминанием
  (карточки как в общей ленте).
- Для проверки заведено 4 тайтла (по фильмам Ghibli/Gainax, которые
  упоминаются в посте «Знакомьтесь: Ёдзи Такэсигэ») и проставлены вручную
  в этом посте полем `anime`.
- **Разметка тайтлов в тексте поста.** В редакторе выделяете нужный кусок
  панели «Аниме» — открывается поиск: печатаете название, снизу появляются
  живые подсказки прямо с Shikimori (если там пусто — пробует AniList),
  с обложкой и годом. Выбираете — в текст вписывается метка со ссылкой
  на конкретный тайтл (по его ID на Shikimori/AniList, не по названию —
  это защищает от путаницы с одноимёнными тайтлами). Технически метка —
  не markdown-ссылка `[Фрирен](anime:frieren)` из черновика тз, а маркер
  вида `:anime[Фрирен]{id="…" source="…" source-id="…"}`: список внутри
  своего блока в CMS в прошлый раз ненадёжно сохранялся (см. этап 2,
  галерея), а тут ещё и нужен живой поиск по внешнему сайту — то же
  решение, что и тогда: маркер в тексте, вся логика — на стороне сайта.
  Код: `public/admin/index.html` (поле поиска и кнопка), `src/plugins/remark-anime.mjs`
  (маркер → ссылка на `/anime/slug` при сборке).
- **Первое упоминание — ссылка, дальше просто текст.** Если тайтл размечен
  в посте два раза, ссылкой становится только первая метка — делает это
  `remark-anime.mjs` при сборке, независимо от того, в каком порядке их
  расставили в редакторе.
- **Поле `anime` у поста больше не нужно вести руками.** При каждом
  сохранении в CMS сама пересчитывает список тайтлов по меткам в тексте
  и дописывает поле — то, что вписано в него вручную (например, тайтл
  упомянут только в подписи к картинке, не в основном тексте), не трогает,
  только добавляет новое сверху. Код — `preSave` в `public/admin/index.html`.
- **Плашки тайтлов под постом** — маленькие карточки с обложкой и названием
  в самом низу страницы поста, по одной на каждый тайтл из поля `anime`.
  Компонент — `src/components/AnimeBadge.astro`.
- **Старые посты (тайтл в поле `anime`, но без метки в тексте) доразмечиваются
  сами при сборке.** Если название тайтла встречается в тексте один в один
  (русское или оригинальное, как в справочнике) — `remark-anime.mjs` сам
  находит первое упоминание и делает его ссылкой, метку в файле поста
  проставлять не нужно. Точное совпадение обязательно: название в другом
  падеже («Ходячего замка» вместо «Ходячий замок») не находится — для таких
  случаев есть поле «Тайтлы поста» (см. ниже). Проверено на живом посте
  «Знакомьтесь: Ёдзи Такэсигэ» после публикации.
- **Поле «Тайтлы поста» в CMS** — на случай, когда тайтл нельзя поймать
  разметкой в тексте (другой падеж, упоминание только в подписи к картинке
  и т. п.). Свой тип поля (не стандартный `relation` — тот не умел искать
  ничего, кроме уже известного): чекбоксы по уже известным тайтлам плюс
  такая же строка живого поиска по Shikimori/AniList, что и у кнопки «Аниме»
  в тексте, — можно добавить и совсем новый тайтл, не вписывая его в текст.
  Выбранное объединяется при сохранении с тем, что нашлось в тексте (ничего
  не перезаписывает). Для нового тайтла CMS не может сама скачать и сжать
  обложку (как и раньше), поэтому подставляет в текст невидимую служебную
  метку `::anime-ref{id="" source="" source-id=""}` — `remark-anime.mjs`
  её убирает, ничего не показывая на странице, а робот на GitHub Actions
  по ней всё равно находит и добирает тайтл, как обычно. Справочник тайтлов
  ради поиска в этом поле дополнительно открыт в CMS отдельной полкой,
  но создавать через неё новые тайтлы нельзя (`create: false`). Код —
  `public/admin/index.html` (виджет `anime-picker`), `public/admin/config.yml`.
- **Новый тайтл на лету.** Когда в редакторе выбираете тайтл, которого ещё
  нет в справочнике сайта, метка в текст всё равно вписывается сразу —
  браузер не может сам скачать и сжать картинку (это делает программа sharp,
  она работает только на сервере, не в браузере, ровно та же причина,
  по которой картинки в постах тоже сжимаются отдельным шагом после сборки).
  Вместо этого через 1–2 минуты после публикации поста автоматически
  срабатывает робот на GitHub Actions (`.github/workflows/sync-anime.yml` →
  `scripts/sync-anime.mjs`): находит в постах метки без файла в справочнике,
  точно по ID (без поиска по названию) добирает данные и обложку — тем же
  кодом, что и `fetch-anime.mjs` (общая часть вынесена в `scripts/anime-lib.mjs`),
  и сам коммитит результат. Руками запускать ничего не нужно; ручной запуск
  `node scripts/fetch-anime.mjs` по-прежнему работает как раньше, если нужно
  завести тайтл заранее (например, до того как он где-то упомянут).
- **Проверка при сохранении.** CMS сверяет текст поста (без учёта уже
  расставленных меток) с названиями тайтлов, которые уже есть в справочнике,
  и если находит непомеченное совпадение — показывает подсказку с именами,
  не блокируя сохранение (решение — за автором).
- **`/anime-index.json`** — список уже известных тайтлов, собирается при
  каждой сборке сайта (`src/pages/anime-index.json.ts`). Нужен только
  админке: чтобы при выборе тайтла, который уже есть в справочнике, не
  плодить второй файл на тот же Shikimori/AniList ID, и для проверки
  на неразмеченные упоминания выше.
- Файлов в сборке: 55 (лимит хостинга — 20 000, запас большой).
- Этап полностью готов — все задачи и пункты приёмки из `тз/03-тайтлы.md`
  закрыты.

## Этап 4. Выпуски и плеер — готово

Разбор RSS, выпуск как пост, страница выпуска, лента, робот сверки, закреплённый
плеер (не прерывается при переходах, перемотка, скорость, таймкоды), раздача
своих видеофайлов на Hetzner с HTTPS, Cyberduck настроен и проверен на живом
файле — всё сделано, все задачи и пункты приёмки из `тз/04-выпуски-и-плеер.md`
закрыты.

- **Мой RSS:** `https://cloud.mave.digital/33503` (хостинг подкаста — Mave).
- **Разбор RSS при сборке** — `src/lib/podcastFeed.mjs`. Свой маленький
  разборщик под конкретные теги фида (title, guid, pubDate, enclosure,
  itunes:duration), без сторонней библиотеки — формат фида стабильный,
  тянуть XML-парсер ради пяти полей не нужно. Фид качается по сети один раз
  за сборку (или запуск робота) и кэшируется в памяти процесса.
  При любой ошибке (сеть недоступна, ответ не похож на RSS) возвращает
  пустой список, не роняя сборку — проверено вручную (симуляция обрыва
  сети и мусорного ответа вместо XML).
- **Выпуск — пост категории `podcast`.** Отдельной сущности для выпуска
  нет, поле `audioGuid` (было в схеме поста ещё с первого этапа)
  связывает пост с конкретной записью в RSS по `<guid>`.
- **Аудио не копируется на сайт.** Ссылку на mp3 сайт при каждой сборке
  берёт прямо из RSS по `audioGuid` — так у хостинга подкаста не
  ломается статистика прослушиваний. На странице выпуска (`/posts/[slug]`)
  это пока обычный `<audio controls>` браузера — проверено на живой
  ссылке (реально отдаёт файл, а не 404). Закреплённый снизу плеер,
  который не прерывается при переходах между страницами, и таймкоды —
  вторая сессия, отдельно от этой работы не трогали.
- **Лента выпусков с фильтром по категории** — отдельную страницу заводить
  не пришлось, `/category/podcast/` с этапа 2 уже показывает ленту именно
  выпусков с теми же вкладками, что и остальные категории.
- **Робот сверки** — `scripts/sync-episodes.mjs` + `.github/workflows/sync-episodes.yml`.
  Раз в день (плюс кнопка «Run workflow» на вкладке Actions для ручного
  запуска) сравнивает RSS со списком постов по `audioGuid` и заводит
  черновик (`draft: true`) с техническими полями — заголовок, дата,
  категория, `audioGuid` — для каждого выпуска, у которого ещё нет поста.
  Имя файла — `ep-<номер>.md`, номер берётся из ссылки на выпуск в самом
  RSS (`.../ep-150` → `ep-150.md`), это свой стабильный ID у хостинга
  подкаста, устойчивее транслитерации заголовка. Уже существующие посты
  (в том числе черновики) робот не трогает никогда — только создаёт
  новые файлы, ничего не переписывает и не удаляет.
- **Первый запуск сделан вручную и закоммичен** — 143 черновика на весь
  архив подкаста (по вашему выбору при обсуждении этого шага: заводить
  сразу весь архив, а не только новые выпуски). Разметку тайтлов
  дописываете сами в CMS, по одному, в своём темпе.
- **В тело черновика тоже подтягивается обложка и описание** — не только
  технические поля, как планировали сначала (добавили по вашей просьбе
  уже после первого запуска). Обложка эпизода (`itunes:image` в RSS) —
  обычной картинкой в начале текста, описание — переводится из HTML
  в markdown своим маленьким конвертером (`src/lib/htmlToMarkdown.mjs`):
  абзацы, списки, жирный/курсив и ссылки сохраняются, незнакомые теги

  не копируем — прямые ссылки на хостинг подкаста, та же причина,
  что и с аудио. Уже написанные вами черновики (или опубликованные)
  при доборе не трогает — правило «заполняем, только если тело
  поста ещё пустое» проверено на живом примере (ep-135, который вы
  уже открывали и правили, — остался нетронутым).

### Вторая сессия: закреплённый плеер и таймкоды

- **Закреплённый плеер внизу экрана, не прерывается при переходах, скрыт,
  пока ничего не запущено.** Технически это включённый в Astro механизм
  «переходов между страницами без полной перезагрузки»
  (`<ClientRouter />` в `src/layouts/Layout.astro`) плюс сам плеер
  (`src/components/PlayerBar.astro`), помеченный `transition:persist` —
  это не хитрость на JS, а буквально одна и та же строка `<audio>`
  в браузере не пересоздаётся при переходе на другую страницу, поэтому
  звук физически не может прерваться.
- **Крестик справа в плеере** — полностью останавливает и «забывает»
  выпуск (не пауза): стирает источник и сохранённую позицию, прячет
  плеер обратно.
- **На странице выпуска — полноценный визуальный плеер** (обложка,
  круглая кнопка play, перемотка, скорость, шкала, время) —
  `src/components/EpisodePlayer.astro`, вместо простой кнопки «Слушать».
  Управляет тем же самым звуком, что и плеер снизу, оба всегда
  синхронны — общий интерфейс `window.__bakaPlayer` в `PlayerBar.astro`.
- **Перемотка на 15 секунд назад/вперёд и выбор скорости** (0.75×–2×) —
  и в закреплённом плеере, и во встроенном в пост.
- **Плеер помнит позицию.** Пока просто переходите по сайту — позиция не
  теряется сама по себе (см. выше про `transition:persist`). Если закрыть
  вкладку или вернуться позже и заново запустить тот же выпуск — сайт
  подставит сохранённую позицию (в памяти браузера, `localStorage`),
  без автовоспроизведения.
- **Автоматические таймкоды.** В тексте постов категории «Подкаст» время
  вида `12:34` или `1:02:03` сайт сам превращает в кликабельную ссылку —
  клик перематывает плеер на нужное место (грузит выпуск, если он ещё не
  запущен). Код — `src/plugins/remark-timecode.mjs`.
- **Запуск с одного клика.** Была ошибка: чтобы перемотать на сохранённую
  позицию перед стартом, `play()` вызывался только после того, как
  приходили метаданные — то есть чуть позже самого клика. Браузер
  из-за этой задержки переставал считать вызов действием пользователя
  и молча блокировал звук (первый клик как будто ничего не делал, второй
  срабатывал). Починено: `play()` вызывается сразу по клику, а перемотка
  на сохранённую позицию — следом, уже во время игры.
- **Попутно нашёлся и починен независимый баг**, не связанный напрямую
  с задачей: система блоков редактора (та же, что обрабатывает «Аниме»/
  «Спойлер»/«Видео») при сборке принимала двоеточие с цифрами сразу после
  (то есть буквально любой таймкод) за начало своей служебной метки —
  и часть текста после такого двоеточия пропадала со страницы. Проверено:
  баг уже подъедал шоуноты в черновиках вроде `ep-100`, `ep-101` (там
  списки таймкодов вида «00:00 — Опенинг»). Почищено для всех категорий
  постов, не только «Подкаста» — это исправление испорченного текста,
  а не часть новой фичи.
- Файлы: `src/layouts/Layout.astro`, `src/components/PlayerBar.astro`
  (новый), `src/components/EpisodePlayer.astro` (новый),
  `src/pages/posts/[slug].astro`, `src/plugins/remark-timecode.mjs`

### Третья сессия: свои видеофайлы на Hetzner

- **Раздача файлов с HTTPS настроена.** На сервере поставлен веб-сервер
  Caddy — раздаёт файлы из папки `/srv/video` по адресу
  `https://167-233-251-252.sslip.io/`. Домена у вас нет, поэтому
  использован sslip.io — бесплатный сервис, который сам превращает
  IP-адрес в доменное имя (по нему Let's Encrypt и выпускает настоящий
  сертификат, обычному IP без домена сертификат не положен). Если позже
  купите домен — просто заменим адрес в конфиге Caddy на ваш, файлы
  трогать не придётся.
- **Отдельный пользователь только для загрузки видео** —
  `videouploader`, доступ по SFTP (это протокол, который использует
  Cyberduck), видит только папку `files` внутри `/srv/video` — она же
  и раздаётся Caddy, поэтому ссылка на файл выглядит как
  `https://167-233-251-252.sslip.io/files/имя-файла.mp4` (путь совпадает
  с тем, что вы видите в Cyberduck — это специально, чтобы ссылку
  не приходилось собирать вручную, см. ниже). Обычного входа в
  командную строку у пользователя нет вообще (технически:
  `ChrootDirectory` + `ForceCommand internal-sftp` в
  `/etc/ssh/sshd_config.d/60-videouploader.conf`) — до остального
  сервера не дотянется, даже если захочет. Пароль от него — только
  у вас, в Cyberduck.
- **Мой (админский) доступ — по SSH-ключу, не по паролю.** Вход по
  паролю для root отключён совсем (`PasswordAuthentication no` в
  `/etc/ssh/sshd_config.d/50-cloud-init.conf`) — временный пароль,
  который использовали при первой настройке через веб-консоль Hetzner,
  уже никуда не пускает. Веб-консоль в панели Hetzner всё ещё работает
  как раньше, от этой настройки не зависит — если что-то случится
  с SSH, вы всегда сможете зайти через неё.
- **Cyberduck настроен и проверен на живом файле.** Закладка на сервер
  с полем «Web URL», указывающим на `https://167-233-251-252.sslip.io` —
  благодаря этому и совпадающим путям (см. выше) пункт меню Cyberduck
  «Copy URL» / «Open URL» у любого файла сразу даёт правильную рабочую
  ссылку, ничего вручную набирать не нужно.
- **Блок «Видео» в редакторе теперь умеет и прямую ссылку на файл**,
  не только YouTube — второе поле в том же блоке. Если заполнены оба —
  побеждает YouTube. Код — `src/plugins/remark-video.mjs`,
  `public/admin/index.html`.
- **Превью-кадр у своих видео.** Было: видео до нажатия play выглядело
  пустым тёмным прямоугольником, как будто не работает (`preload="none"`
  не грузил вообще ничего). Починено на `preload="metadata"` — браузер
  подгружает первый кадр, не скачивая файл целиком.
- Файлов в сборке сайта эта часть почти не касается — на сервере
  проделана отдельная работа, в коде сайта поменялся только блок «Видео».

## Этап 9. Отложенная публикация — готово (кроме одного ручного шага)

Сделано раньше этапов 5–8, по отдельной просьбе — из архива готова публикация
задним числом и по расписанию, все задачи и пункты приёмки из
`тз/09-отложенный-постинг.md` закрыты, кроме уведомления на почту (см. ниже).

- **`date` и `publishAt` — независимые оси**, как и было задумано в ТЗ:
  `date` — только для отображения и сортировки (в том числе задним числом,
  без предупреждений и блокировок), `publishAt` — только для того, видно ли
  пост на сайте. Общая проверка — `src/lib/publishing.mjs` (`isPublished`),
  подключена везде, где раньше стояла проверка `!data.draft`: лента на
  главной, страницы категорий, страница отдельного поста.
- **Как это выглядит для автора.** Пост пишется как обычный черновик
  (галочка «Черновик» стоит). Чтобы запланировать — заполняется только
  новое поле **«Когда опубликовать»**, галочку трогать не нужно: её снимает
  сам робот, ровно когда время наступает. Чтобы перенести — правится дата.
  Чтобы отменить — дата стирается, пост остаётся обычным черновиком, как
  до простановки даты. Часовой пояс в этом поле — явно Берлин
  (`input_timezone: Europe/Berlin`, `output_utc: true` у Sveltia CMS,
  см. `public/admin/config.yml`): время в админке показывается ваше,
  не UTC, и не зависит от часового пояса браузера или сервера сборки.
- **Пометка в общем списке постов** — `⏰ 12.09, 10:00` рядом с названием
  у запланированных, `· черновик` у обычных черновиков без даты, ничего
  лишнего у уже вышедших. Реализовано шаблоном `summary` в конфиге CMS
  (без своего кода — Sveltia умеет такие шаблоны из коробки).
- **Предпросмотр запланированного поста** — отдельной страницы не заводили:
  запланированный пост черновик, свой страницы на сайте у него нет
  (как и у обычных черновиков), но живой предпросмотр текста уже даёт
  сама CMS (панель справа в редакторе) — этого достаточно, ничего
  усложнять не пришлось.
- **Робот-будильник — отдельный воркер `publish-cron/`**, Cloudflare Cron
  Trigger, расписание раз в минуту (`* * * * *` в `publish-cron/wrangler.jsonc`) —
  самое частое, что позволяет Cloudflare, ради точности «пост выходит не
  позже чем через 3 минуты после назначенного времени». Каждую минуту
  смотрит на маленький список запланированных постов
  (`/publish-queue.json`, генерируется при каждой сборке сайта —
  `src/pages/publish-queue.json.ts`), и если публиковать нечего — не делает
  вообще ничего (ни одного обращения к GitHub), чтобы не тратить впустую
  сборки. Если что-то наступило — снимает `draft: true` → `draft: false`
  прямо в файле поста через GitHub API (у воркера нет git, только HTTP),
  коммитит от своего имени — коммит запускает уже существующую автосборку.
- **Связь между воркерами — через Service Binding, не через публичный
  адрес.** При первом же живом тесте выяснилось: когда `publish-cron`
  обращался к сайту по обычному адресу `https://baka-page…workers.dev/…`,
  получал 404, хотя тот же адрес снаружи (curl, браузер) открывался
  нормально — известная особенность Cloudflare, обращение воркера
  к воркеру на одном аккаунте лучше делать напрямую. Исправлено —
  `services: [{ binding: "SITE", service: "baka-page" }]` в
  `publish-cron/wrangler.jsonc`, в коде `env.SITE.fetch(...)` вместо
  обычного `fetch(URL)`. После этого сквозной сценарий (запланировал →
  робот сам снял черновик → сайт опубликовал) проверен на живом тестовом
  посте и отработал без участия человека.
- **Известная проблема с неполной автосборкой (см. этап 2) — всё ещё
  изредка проявляется, не блокирует.** В истории сборок Cloudflare
  (вкладка Build history) все сборки успешны, каждый пуш собирается —
  то есть сама сборка не срывается. Но раздача файлов на edge-серверах
  после свежего деплоя иногда на 1–2 минуты показывает вперемешку старое
  и новое (в тесте страница нового поста несколько раз подряд отвечала
  то 404, то 200, прежде чем устаканиться сама) — это несмотря на то,
  что основную причину (кэширование предыдущих версий) уже отключили
  в другой сессии, см. этап 2. Похоже, реже, но не исчезло совсем.
  Это может изредка сдвигать момент, когда пост реально становится
  виден, на минуту-другую сверх заявленных 3 минут — но чинится само,
  без ручного `wrangler deploy`. Если после этого этапа замечаете, что
  запланированный пост вышел с ощутимым опозданием — сначала проверьте
  этот пункт и пункт про кэширование в этапе 2, скорее всего дело в них,
  а не в роботе.
- **Уведомление на почту при сбое (пункт 7 из ТЗ) — не автоматизировано
  мной, нужен один ручной шаг в панели Cloudflare** (раздел Notifications):
  добавить оповещение на неудачную сборку воркера `baka-page` и на ошибки
  выполнения воркера `baki-publish-cron`. Не смог настроить через API —
  у токена wrangler нет прав на раздел уведомлений, а через браузер в этой
  сессии не получилось. Как только сделаете — этот пункт можно считать
  закрытым, отдельно фиксировать в статусе не нужно.
- **Ручной запуск робота для отладки** — `POST /run` с заголовком
  `x-run-token: …` (секрет `RUN_TOKEN` в Cloudflare, отдельно от
  `GITHUB_TOKEN`) у `https://baki-publish-cron.eduard1414ed.workers.dev/run`.
  Не обязателен для обычной работы (расписание срабатывает само), пригодится,
  если понадобится проверить робота, не дожидаясь реальной минуты.
