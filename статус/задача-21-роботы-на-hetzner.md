**Начата 25 августа 2026.** Причина: пометка «спам» на аккаунте GitHub
выключила Actions, восемь роботов молчат
([задача-20](задача-20-флаг-github.md)).

**Сделана первая часть: один робот — добор выпусков из RSS.** Остальные семь
и автосборка — следующими сессиями.

## Что сделано

Робот `sync-episodes` переехал с GitHub Actions на systemd сервера Hetzner.
**Логика не менялась ни строкой** — зовутся те же скрипты, в том же порядке,
с теми же ключами. Изменился только тот, кто их запускает.

Расписание прежнее: **каждый день в 06:00 UTC, 09:00 по Москве.**

## Секреты

**В репозиторий не попал ни один, и это проверено** — не только поиском слов
вроде «token», а поиском *значений, похожих на ключи*: длинные случайные
строки, характерные префиксы, присваивания с непустым значением. Проверку
предварительно уронили подложенным поддельным ключом — она его поймала,
значит её «чисто» чего-то стоит.

Роботу нужны **два** секрета, и оба уже на месте:

| Ключ | Где | Кто вписал |
|---|---|---|
| Токен телеграм-бота и номер чата | `/root/baka-secrets/telegram.env` | заказчик, руками |
| ElevenLabs (платная расшифровка) | `/root/baki-transcripts/.env` | лежал с прошлых прогонов |

Ключи Mave, Shikimori, московского хранилища и Cloudflare этому роботу
**не нужны вовсе** — проверено поиском обращений к переменным окружения
во всех трёх скриптах. Они понадобятся тем роботам, что переезжают позже.

## Доступ к GitHub: deploy key не сработал

Сначала завели **ключ репозитория** (deploy key) — узкий доступ, как правильно.
GitHub его принял: `verified: true`, право записи есть, аутентификация
проходит, сервер получает `Hi eduard1414ed/Baka-page!`.

**И всё равно `ERROR: Repository not found`.**

Проверено, что дело не в глупой причине: ключ добавлен верно (сверено через
API), уходит именно он (виден в подробном логе ssh), отпечаток совпадает.
С машины заказчика в ту же минуту работали оба пути — и SSH, и HTTPS.

**Вывод: пометка «спам» гасит и deploy keys.** Картина ровно та же, что
с квотой API: механизм формально жив, ключ признан, а доступа нет.

**Решением заказчика** на сервер положен ключ аккаунта (`/root/.ssh/github_account`,
права 600). Довод — под этим аккаунтом всего два репозитория, проверено:
`Baka-page` и приватный `calendar-jr`. Риск принят осознанно.

Неработающий deploy key остался висеть в настройках репозитория — вреда
от него нет, а снимут пометку — пригодится.

## Повторной оплаты расшифровки не будет

Проверено до первого запуска, потому что цена ошибки денежная.

`auto.py` решает, что расшифровывать, **по наличию файла
`src/content/transcripts/<guid>.json` в репозитории** — не по журналу
на машине. Клон видит все 143 оплаченные расшифровки и пропускает их.
Это тот самый способ, который переживает смену машины.

Холостой прогон (`--dry-run`) на сервере ответил дословно: **«Расшифровывать
нечего: у всех выпусков из RSS транскрипт уже есть»**.

Два выпуска без файла расшифровки — `ep-1` («Опенинг») и `ep-23` («Трейлер
подкаста „Вжик“…») — **и не должны его иметь**: оба подпадают под исключения
`SKIP_EXACT_TITLES` и `SKIP_TITLE_PARTS`, записанные решением заказчика ещё
раньше. Ничего дописывать не потребовалось.

## Как узнать, что робот жив

Заказчик выбрал: **телеграм плюс отметка в репозитории.**

Бот `baka_hetzner_bot` («Baka Сервер») пишет **после каждого захода** —
и это сделано нарочно, вопреки обычному правилу «письмо только когда
не вышло». Требование задания: *молчание не должно выглядеть как «всё
хорошо»*. Раз сообщение приходит каждый день, то его отсутствие и есть
сигнал тревоги.

| Что случилось | Что придёт |
|---|---|
| Новый выпуск, обложка или расшифровка | 🟢 **есть новое**, с перечнем |
| Сходил, новостей нет | ⚪️ **сходил, новостей нет** |
| Что-то не вышло | 🔴 **не доделал работу**, со списком причин и путём к журналу |

Отметка в репозитории — это сами коммиты робота (`baka-episodes-bot`):
завёл черновик, вырезал персонажа, добавил расшифровку.

**Чего эта схема НЕ ловит:** если сервер выключится совсем, тревожного
сообщения не будет — мёртвый сервер молчит. Заметно это станет по отсутствию
ежедневного сообщения. Внешний сторож (healthchecks.io), который ловит именно
этот случай, заказчиком отклонён.

## Переживает перезагрузку — проверено по-настоящему

Сервер перезагружен командой `systemctl reboot` 25 августа.

| | До | После |
|---|---|---|
| таймер робота | enabled / active | **enabled / active** |
| следующий заход | 26.08 06:00 UTC | **26.08 06:01 UTC** |
| Caddy | active | **active**, файл отдаётся кодом 200 |
| телеграм-бот | active | **active** |

Прогон робота после перезагрузки: код 0, `Result=success`, ошибок ноль.

В расписании стоит `Persistent=true` — если в 06:00 сервер будет выключен,
запуск не потеряется, робот сходит сразу после включения.

## Время работы

| | |
|---|---|
| Прогон робота на сервере | **5 секунд** (08:38:58 → 08:39:03) |
| Прогон на GitHub Actions | **неизвестно точно**: журнал прогонов унесён пометкой. По составу шагов (checkout, установка Node, `npm ci`, ffmpeg, pip) — минуты, не секунды |

Разница объяснимая: на сервере окружение уже стоит, а Actions собирали его
заново каждый раз.

**Сборка сайта на сервере: 5 минут 45 секунд** (1408 страниц, все проверки
зелёные, памяти хватило). Против **52–79 секунд у Cloudflare** — то есть
в 4–7 раз дольше. Это важно для автосборки в следующей сессии: «сохранил
пост → через минуту на сайте» станет «через 6–7 минут».

## Старый воркфлоу

Не удалён, а **переименован** в `.github/workflows/sync-episodes.yml.disabled`.

GitHub Actions читает только `.yml` и `.yaml` — значит он не запустится, даже
если Actions внезапно оживут. Возврат: переименовать обратно, предварительно
выключив серверный (`systemctl disable --now baka-episodes.timer`), иначе два
робота подерутся за пуш. Внутри файла это записано первым же комментарием.

## Кнопка на /admin/tools/ — оценка, не сделано

Сейчас кнопка «Забрать новые выпуски подкаста» зовёт
`/repos/…/actions/workflows/sync-episodes.yml/dispatches` — то есть Actions,
которых нет.

Чтобы она звала робота на сервере, нужно:

1. **Способ позвать сервер из браузера.** Сервер снаружи доступен только
   по SSH и через Caddy. Значит нужен маленький обработчик — путь в Caddy,
   который по секретному адресу запускает `systemctl start baka-episodes`.
2. **Защита от чужих.** Адрес обязан быть непубличным, иначе робота сможет
   дёргать кто угодно.
3. **Показ, что робот пошёл и чем кончилось.** Сейчас это видно в телеграме;
   на странице нужен опрос состояния.

Оценка: **половина сессии.** Отдельная работа, и делать её стоит после того,
как робот поживёт по расписанию хотя бы сутки.

## Чего НЕ проверено

- **Робот ни разу не отработал по настоящему расписанию** — все прогоны
  запускались руками. Первый самостоятельный заход назначен на 26 августа 06:01 UTC.
- **Не проверено поведение при реально новом выпуске:** в RSS сейчас нет
  ничего, чего не было бы постом. Значит ветки «завёл черновик», «вырезал
  персонажа», «расшифровал» на сервере не исполнялись ни разу — они прошли
  только вхолостую.
- **Не проверено падение расшифровки** и то, как выглядит тревожное письмо
  при настоящем сбое (ложную тревогу видели — она пришла из-за ошибки в моём
  скрипте, и это скорее удача).
- **Не проверено, что будет при обрыве сети** посреди пуша.
