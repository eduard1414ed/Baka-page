# Задача: правило индексируемости страниц тайтлов

## Что делаем и зачем

Сейчас в индекс отдаются все 658 страниц тайтлов. Почти половина из них держится
на одном упоминании без таймкодов — там нет собственного содержания, только синопсис
из внешнего источника и одна карточка со ссылкой. Такие страницы разбавляют домен
и мешают ранжироваться сильным.

Нужно сделать индексируемость **вычисляемым свойством страницы**, которое пересчитывается
при каждой сборке. Не разовая расстановка флагов: сайт живой, упоминания копятся,
страница должна входить в индекс сама, когда наберёт вес.

**Ничего не удаляем и не прячем от пользователя.** Все 658 страниц остаются на сайте,
доступны по ссылкам, работают в навигации и внутреннем поиске. Меняется только то,
отдаются ли они поисковым системам.

## Правило №1

Репозиторий сайта — рабочий. Меняем только то, что перечислено ниже. Никаких попутных
рефакторингов, переименований и «заодно поправил».

## Правило №2

Формула ниже — начальная. Она подобрана по фактическому распределению (медиана 2 упоминания,
45 % страниц с одним). Пороги должны лежать в конфиге одним местом, а не быть размазаны
по коду: их придётся крутить.

---

## 1. Формула

Для каждой страницы тайтла считается:

```
score = own_mentions + 2 * has_timecodes + podcast_mentions
index = score >= 3
```

Где:

- `own_mentions` — число уникальных **собственных** материалов в блоке «упоминания»
  (подкаст, заметка, видеоэссе, статья со своей страницей). Записи с `externalUrl`
  сюда **не входят**.
- `has_timecodes` — 1, если на странице есть хотя бы один таймкод, иначе 0.
- `podcast_mentions` — число упоминаний категории `podcast`.

Внешние упоминания не учитываются в score, но и не штрафуют. Страница с одними внешними
упоминаниями просто ждёт, пока наберёт своих.

Пороги и веса вынести в конфиг:

```js
// src/config/indexability.js
export const INDEXABILITY = {
  weights: { own: 1, timecodes: 2, podcast: 1 },
  threshold: 3,
  maxStatusChangesPerBuild: 40,
};
```

**Ожидаемый результат на текущих данных:** примерно 261 страница в индексе, 397 закрыто.
Если получилось радикально иное — не подгоняй формулу под цифру, покажи мне расхождение.

## 2. Ручное переопределение

Поле во фронтматтере тайтла, перебивающее формулу в обе стороны:

```yaml
forceIndex: true   # всегда в индекс
forceIndex: false  # всегда закрыто
```

Отсутствие поля — работает формула. Переопределения логировать отдельно (см. п. 4),
чтобы было видно, сколько страниц выведено из-под правила.

## 3. Применение флага — в двух местах, из одного источника

Критично: разметка и sitemap должны получать флаг из одной функции. Расхождение между ними
даёт поисковику противоречивый сигнал, и это худший из возможных исходов.

1. **В `<head>` страницы тайтла**: если `index === false` — `<meta name="robots" content="noindex, follow">`.
   Именно `follow`, а не `noindex, nofollow`: ссылки со страницы должны продолжать
   передавать вес на посты.
2. **В `sitemap.xml`**: страницы с `index === false` в карту не попадают.

Проверь, как сейчас генерируется sitemap (интеграция Astro или свой скрипт), и подключи
фильтр туда же. Если sitemap собирается плагином, у которого нет хука фильтрации —
скажи мне, решим отдельно, не изобретай обход.

## 4. Лог переходов

При каждой сборке писать `build-logs/indexability-YYYY-MM-DD.json`:

```json
{
  "builtAt": "2026-08-30T18:00:00Z",
  "total": 658,
  "indexed": 261,
  "excluded": 397,
  "forced": { "in": 3, "out": 1 },
  "entered": ["dorohedoro", "..."],
  "left": [],
  "scoreDistribution": { "0": 87, "1": 212, "2": 98, "3": 76 }
}
```

`entered` и `left` считаются диффом с предыдущим логом. Если предыдущего нет — первая
сборка, оба массива пустые, это нормально.

**`left` в норме должен быть пустым всегда**: упоминания только накапливаются, страница
не может потерять вес. Любая непустая `left` — признак, что поехали данные (обычно
ломается матчинг названий). Выводить её в консоль предупреждением.

## 5. Стоп-кран

Если число изменений статуса за сборку превышает `maxStatusChangesPerBuild` (40) —
**сборка падает с ошибкой**, а не применяет изменения тихо.

Текст ошибки должен объяснять, что делать: показать число изменений, первые десять слагов,
и подсказать, что если изменение ожидаемое (поменяли формулу) — запустить с флагом
`ALLOW_INDEX_SHIFT=1`.

Смысл: если отвалится регулярка в матчинге названий, половина сайта выпадет из индекса
молча, и узнаешь ты об этом через месяц по обвалу показов.

## 6. Отчёт для человека

Команда `npm run indexability:report` (или как принято в проекте), печатает в консоль:

- распределение score
- сколько страниц в индексе, сколько закрыто
- топ-20 страниц у самой границы (score 2 и 3) — это те, чья судьба решается порогом,
  по ним удобно проверять, адекватна ли формула
- список `forceIndex` переопределений

Ничего никуда не отправляет, просто печатает.

## Порядок работы

1. Сначала посчитай формулу **без применения** и покажи мне: распределение score,
   сколько попадает в индекс, топ-20 пограничных страниц. **Остановись здесь.**
2. После подтверждения — реализуй п. 2–6.
3. Прогони сборку, покажи лог и убедись, что `left` пустой.

## Чего не делать

- Не удалять и не скрывать страницы от пользователей
- Не трогать синопсисы и порядок блоков на странице
- Не менять `canonical` (это отдельная задача)
- Не добавлять `nofollow` — только `noindex, follow`
- Не подгонять формулу под ожидаемые 261/397, если данные говорят иное
- Не применять изменения при сработавшем стоп-кране
